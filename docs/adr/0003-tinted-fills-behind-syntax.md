# Tinted fills behind syntax text

Diff lines, breakpoints, the execution point, write-usage highlights, conflict markers and status fills all sit behind syntax text, so ADR 0001's bar applies to them: every syntax role reaches 4.5:1. Rather than add an opaque palette colour for each, every such fill is a status, accent, or magenta colour composited over the background at one alpha per appearance, `33` in Geist Dark and `1a` in Geist Light (`TINT_ALPHAS` in `build.py`). Those are the strongest alphas at which every tint keeps comments, always the weakest role, at 4.5:1. Geist Light's comment is only 5.27:1 on its background, so its ceiling is about `1a` (deleted lines 4.52:1), while Geist Dark has room up to `3b`. One alpha per appearance keeps a single rule across targets, and `build.py` stops the build if a tint, or any other surface behind syntax text, drops a role below 4.5:1.

A palette can set its own `tint_alpha`. Brzz Dark uses `1a`, the light default: it keeps its syntax colours near 5.5:1 on the background, where its yellow conflict and warning tints at `33` would have pushed them to 7:1, losing the softer look it exists for. Its diff and diagnostic fills are fainter in exchange.

JetBrains' write-usage highlight used a fixed `33` keyword tint, which left Geist Light's comments at 3.86:1 on it, so it now takes the shared tint too. That tint takes the ANSI magenta rather than the keyword colour, which is purple in Geist but orange in Ayu, where a write highlight would sit too close to the gold accent's fills, such as the execution point.

The headroom rules out a second, brighter fill for the changed words inside a changed line. VS Code paints `diffEditor.insertedTextBackground` over `insertedLineBackground`, and two Light tints stacked drop comments to about 3.97:1, so VS Code's changed text gets no fill of its own. A border in the status colour could mark changed words instead, but VS Code applies the changed-text decoration to wholly changed lines too, which boxed every changed line, so we leave it out. Zed has no border for word diffs, so its word fills equal its hunk fills. In both, changed words inside a line aren't singled out. We accept losing that emphasis rather than put text below the bar.

Claude Code is the exception to the bar itself. It paints diff code in its own highlighter's colours, Monokai Extended over a `dark` base and GitHub over a `light` one, and no theme key reaches them; some already fall below 4.5:1 on a plain background (Monokai's comment is 4.28:1 on Geist Dark's, GitHub's 2.81:1 on Geist Light's). So `build.py` can't hold them to the bar, and Geist only keeps them from losing more where it can: its diff line fills are the tints, and its rejected-edit fills composite at half the tint's strength, nearer the background. Its word keys can't stay faint, because Claude Code also draws the `+N` and `−N` line counts in them as text, so they take the status colours themselves, as Claude Code's own themes do, and changed words get a strong fill behind the highlighter.

VS Code draws decorations over the selection, and asks for translucent fills so they don't hide it. Its diff lines, stack frames, word and hover highlights, linked edits and snippet tabstops therefore take a translucent colour at alpha `80`. Over the current-line highlight (`ui.hover`), where the cursor sits on a stopped debugger line, it composites to the opaque tint or highlight that `build.py` checks. Over the plain background it lands further from every syntax colour, because Geist Dark's background is darker than its current line and Geist Light's lighter, so text gains contrast there; a palette that reversed that order would need this rechecked. Over a selection, the blend of the two isn't held to 4.5:1, the same exception ADR 0001 makes for Zed's selection over a highlight. Find matches stay opaque, as ADR 0002 decided.
